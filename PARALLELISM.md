# Параллельная обработка данных

Ветка: `feature/parallel_processing`

Цель — ускорить обработку за счёт одновременного выполнения **независимых**
операций. Ключевое слово — независимых: параллелить можно только то, что не
делит между собой изменяемое состояние.

---

## Инструмент

`Shared/Concurrency/ConcurrentMap.swift`

```swift
let vectors = await texts.concurrentMap(maxConcurrent: 4) { await embed($0) }
```

Три свойства, ради которых написана обёртка над `withTaskGroup`:

1. **Ограничение параллелизма.** Без него 500 элементов = 500 одновременных
   запросов: rate limit от провайдера и всплеск памяти. Скользящее окно держит
   в полёте не более `maxConcurrent` задач.
2. **Сохранение порядка.** Задачи завершаются в произвольном порядке; результат
   пересобирается по индексам, поэтому вызывающий код не меняется.
3. **Реакция на отмену.** При `Task.cancel()` новые элементы не запускаются.

Пресеты в `ConcurrencyLimit`: `network` (4), `onDeviceLLM` (2), `cpu` (по ядрам).

## Что распараллелено

| Место | Было | Стало |
| --- | --- | --- |
| `SemanticSearchService.reindexAll` | N embedding-запросов по очереди | окно 4, запись в БД после |
| `RelatedMemoriesService.findRelated` | вектор источника + N векторов кандидатов последовательно | `async let` + пакетный `vectors(for:)` |
| `SemanticSearchService.search` | два чтения БД по очереди; hop на актор на каждой итерации скоринга | `async let` для чтений; косинус — `nonisolated` |
| `ImportService.importAll` | Calendar, затем Photos | одновременно, порядок результатов сохранён |
| `EntityExtractionService` | N извлечений + N транзакций | окно 2, одна запись в БД |
| `RememberApp` фоновая индексация | два `fetch` по очереди, затем цикл | `async let` + пакетные операции |

Дополнительно: `LLMProviderService` кэширует провайдеры. Раньше каждое обращение
к `.embedding` создавало объект и читало Keychain — в параллельном цикле это
сотни обращений, которые система сериализует и съедают весь выигрыш.

## Главный урок: параллелизм вскрывает скрытые гонки

`AppleEmbeddingProvider` был помечен `@unchecked Sendable` с комментарием
«NLEmbedding thread-safe для чтения». Последовательный код это утверждение
никогда не проверял. Первый же параллельный прогон дал:

```
Remember(57290) malloc: Heap corruption detected, free list is damaged
*** Incorrect guard value: 3345452569300959327
```

`NLEmbedding.vector(for:)` не рассчитан на одновременные вызовы. Провайдер стал
актором — доступ к модели сериализован.

Следствие: **на Apple-провайдере параллелизм embeddings выигрыша не даёт** —
операция CPU-bound и защищена актором. Выигрыш реален там, где время уходит на
ожидание: сетевые провайдеры (OpenAI, Gemini), импортёры, независимые чтения БД.

Правило: `@unchecked Sendable` — это обещание, а не проверка. Перед тем как
распараллелить вызов, нужно убедиться, что обещание кто-то выполняет.
